The platform combines a React client, Express/Node backend, MongoDB persistence, Redis-backed real-time infrastructure, AI-assisted career workflows, third-party developer intelligence, and an Android Capacitor wrapper. The report separates verified implementation from configuration-dependent behavior and planned scope.

1.1 Problem Context

Traditional alumni directories are primarily identity stores. They often do not provide an integrated workflow for discovering mentors, requesting guidance, communicating in real time, finding jobs, showcasing projects, tracking developer activity, and obtaining structured career assistance. Alumnex Connect addresses that fragmentation by combining professional-network functions with operational workflows.

1.2 Project Objectives

  • Provide a role-aware platform for students, alumni, administrators and college-oriented users.
  • Support mentorship discovery, requests, sessions, reviews and mentor-oriented metadata.
  • Provide career opportunities, job applications and AI-assisted job/resume workflows.
  • Enable discussion, networking, real-time messaging and notifications.
  • Aggregate public developer activity from multiple external platforms into a unified profile.
  • Provide layered security, external-service fallbacks and operational resilience.
  • Reuse the web application inside an Android wrapper rather than maintaining a completely separate

native feature set.

3.1 High-Level Architecture

Figure 3.1 - High-level Alumnex Connect architecture

The application follows a decoupled client-server model. Browser users interact with a React SPA; the same web build is also packaged through Capacitor for Android. The client communicates with the Node/Express server through HTTP APIs and Socket.IO. The backend persists domain data in MongoDB, uses Redis where configured for caching/pub/sub behavior, and communicates with external providers for authentication, AI, file delivery and developer-data aggregation.

3.2 Request Lifecycle

Observed request-processing layers Client request -> CORS / security headers -> rate limiting -> body + cookie parsing -> CSRF processing -> NoSQL sanitization + HPP -> authentication (where protected) -> authorization / ownership

-> route validation -> service / business logic -> MongoDB / Redis / external API -> response or centralized error handling

The key architectural characteristic is that the application does not rely on a single “security check”. Request acceptance is layered. Likewise, availability is not delegated to one mechanism: the frontend can switch API endpoints, AI requests can switch provider, and some local Redis-dependent behavior can degrade into a mock cache implementation.

3.3 Resilience Architecture

Figure 3.2 - Generic failure/fallback decision pattern observed across the system

The most important distinction is between independent fallback domains. Backend endpoint failover is a client-side mechanism. AI failover is service-level provider orchestration. Redis fallback is a runtime capability choice. GitHub developer-stat fallback is provider-specific. These should not be described as one generic load balancer; they are separate mechanisms that reduce single points of failure at different layers.

5.3 Lazy Loading and Suspense

Major pages are imported with React.lazy and rendered under Suspense. This turns route modules into asynchronously loaded chunks rather than forcing the entire feature surface into the initial bundle. The application also places the route tree under an ErrorBoundary, creating a separate failure boundary for rendering errors.

5.4 Server-State Policy

Policy Observed value Engineering implication

Retry No retry for 401/403/404; otherwise up to Auth and authorization errors are not 2 retries pointlessly retried

Backoff min(1000 * 2^attempt, 10000) Avoids immediate repeated requests

Window focus refetch Disabled Reduces background refresh traffic

Stale time 2 hours Navigation can reuse cached server state

Cache time 3 hours Data can persist in memory beyond stale window

Mutations No automatic retry Avoids accidental duplicate writes

5.5 Offline Awareness

The frontend registers online and offline browser events and displays a high-priority banner when navigator.onLine becomes false. This is a user-experience safeguard rather than a complete offline application: the message explicitly warns that some features may not work.

5.6 HTTP Client Resilience

The Axios wrapper is one of the most technically distinctive frontend files. It detects Capacitor, maintains a mobile token store, constructs a candidate backend URL list, randomizes the initial backend when more than one endpoint is available, fails over on network/timeout errors, queues concurrent requests during token refresh, distinguishes auth failures from network failures, and exposes a Promise.allSettled helper for independent parallel requests.

6.4 Error and Process-Level Safety

The server has a centralized error handler that logs the error stack and deliberately avoids exposing internal stack details in production. A bottom-of-stack wildcard handler returns a 404 JSON response. Process-level listeners log unhandled promise rejections and uncaught exceptions. These are not substitutes for graceful shutdown or process supervision, but they demonstrate deliberate attention to failure visibility and information disclosure.

7.3 User Model Behaviors

  • Password hashing uses bcrypt with a generated salt of 12 rounds before save when the password is

modified.

  • comparePassword() delegates candidate verification to bcrypt.
  • updateLastActive() performs a targeted update rather than requiring the whole document to be saved

synchronously.

  • getPublicProfile() removes password and __v from the returned object.
  • isOnline is computed from activity within a five-minute window.
  • Indexes exist for alumni company, skills, role/status, alumni industry and location.
  • A document delete hook removes related forum posts, messages, mentorships, notifications and jobs and

cleans relationship arrays in other users.

9.2 CSRF Behavior in Detail

The custom CSRF middleware generates a random 32-byte hexadecimal token when the XSRF cookie is absent, exposes the token through the response header, skips validation for GET/HEAD/OPTIONS, bypasses the state- changing check for the Capacitor marker, and in production returns HTTP 403 when the header is missing or mismatched. Development mode intentionally allows requests through after logging a warning. That development bypass is a configuration trade-off, not a production security feature.

⌁Evidence SEC1: backend/middleware/csrf.js - token creation, safe methods, mobile exception and production

enforcement

9.3 Residual Risks

  • The mobile path stores a bearer token in localStorage. This is a conscious architecture trade-off for the

wrapper environment and carries greater token-extraction risk on a compromised device than an HttpOnly cookie.

  • Client-side backend failover improves availability but is not equivalent to a managed infrastructure load

balancer or global traffic manager.

  • The report should not assume file malware scanning, distributed rate-limiting, automated secret rotation

or full observability unless additional evidence exists.

  • External scraping and third-party APIs remain subject to upstream schema/rate-limit changes.

10.1 Mentorship

The mentorship domain includes distinct models for mentorship requests, active mentorship relationships, sessions, mentor reviews and rewards. The User model itself contains mentor readiness fields such as availability, maximum mentees, preferred batches, rating, review count and accumulated mentorship hours. The authorization layer further restricts mentor eligibility to active, approved alumni.

10.2 Jobs and Resume Analysis

The job domain combines conventional listing/application workflows with AI-assisted analysis. The resume- analysis route accepts a PDF, checks MIME type, parses the file from memory using pdf-parse, constructs a structured prompt containing the job description and extracted resume text, requests strict JSON output from the AI orchestrator, strips code-fence wrappers if present, extracts a JSON object and parses it before returning structured analysis.

Resume analysis processing chain PDF upload -> multipart memory buffer -> MIME check == application/pdf -> pdf-parse -> resume text -> JD + resume prompt -> Groq / Gemini -> remove markdown fences -> extract JSON object -> JSON.parse -> structured ATS response

⌁Evidence M1: backend/routes/ai.js - resume upload, MIME validation, pdf-parse and response parsing

10.3 Forum and Moderation

The forum route imports a moderation utility, user and notification models, and the AI helper. This indicates that the discussion subsystem is not purely a CRUD post store; moderation and notification-related behavior are part of its implementation surface. Exact trigger matrices should remain tied to the route code when extending this chapter with further endpoint-level evidence.

10.4 Developer Intelligence

The developer profile fetcher normalizes usernames before hitting external services, strips leading @ signs, handles profile URLs, uses parallel requests where useful, preserves partial success through Promise.allSettled, and applies provider-specific fallbacks. The GitHub implementation prefers GraphQL for rich data and falls back to the v3 REST endpoint when GraphQL fails. GFG parsing first attempts embedded JSON and then falls back to regex extraction.

11.3 Demonstration / Mock Mode

Several AI endpoints deliberately return deterministic demo output when neither Groq nor Gemini credentials are present. This is an important distinction: demo mode proves that the UI workflow can operate without a live provider, but it is not equivalent to live model inference. The final report therefore classifies this behavior as a fallback/demo mechanism rather than as AI capability itself.

11.4 Output Robustness

For JSON-oriented AI tasks, the implementation requests a JSON response mode where supported, then defensively removes markdown fences and extracts the first JSON object-shaped block before parsing. This is a lightweight normalization layer aimed at common formatting deviations from model output.

12.1 Client Socket Lifecycle

The SocketContext creates a Socket.IO connection only when a user exists. On logout or user removal it disconnects and clears state. It tracks isConnected, maintains an online-user map, joins a personal user room, requests current online users, reacts to user online/offline events, and marks a user away/back based on browser visibility. Cleanup removes event listeners and disconnects the socket on unmount.

12.2 Socket Failover

Socket connection failures trigger the same backend failover mechanism used by the Axios client. If HTTP failover changes the active backend, a backend-failover custom event is emitted so SocketContext can swap its Socket.IO URI to match the new backend and reconnect. This is a strong cross-layer consistency mechanism: API and WebSocket traffic are intentionally kept pointed at the same active backend.

14.1 Redis Runtime Modes

The cache utility has two implementations: a real Redis client and a mock cache. Real Redis is selected in production or when REDIS_URL is present. Otherwise a mock client exposes the same method names expected by dependent code. The real client serializes values, applies an EX TTL, and catches get/set/delete errors so cache failures can degrade into cache misses or falsey writes rather than directly crashing application flows.

15.1 Important Trade-offs

  • Long React Query stale windows improve responsiveness but increase the age of data reused from cache.
  • A 60-second Axios timeout reduces false failure during cold-start recovery but can make a genuinely

unavailable request feel slow.

  • Client-side endpoint failover improves resilience but retains endpoint-selection state inside the client

process rather than an infrastructure control plane.

  • In-memory PDF handling is simple, but memory usage scales with upload size and concurrency;

production-grade systems may move this work to a queue or object storage pipeline.

18.1 Mobile Authentication Trade-off

The browser and mobile paths do not share identical cookie assumptions. The frontend API utility detects Capacitor environments and keeps a JWT in localStorage, then adds an Authorization Bearer header and the mobile marker used by the backend CSRF middleware. This makes the mobile path operational in a WebView environment where cross-origin cookie behavior can be unreliable, but it changes the token-exposure model compared with HttpOnly browser cookies.

20.2 Conclusion

Alumnex Connect is best understood as a multi-domain full-stack platform rather than a single-feature alumni directory. Its implementation includes a React application with substantial route-level code splitting and server-state policies, a Node/Express backend with layered security and authorization, MongoDB/Mongoose models with indexes and lifecycle hooks, Socket.IO real-time capabilities with Redis adapter support, AI provider orchestration with explicit fallback paths, external developer-data aggregation, managed media integration, and a Capacitor-based Android delivery path. The strongest evidence of engineering depth is the set of cross-cutting mechanisms that address failure, not simply the number of pages or libraries.

For academic/evidence purposes, the most defensible claims are the ones tied directly to source files and functions. This report therefore treats the repository as the implementation record and explicitly separates verified mechanisms from documentation-only or configuration-dependent capabilities. That approach makes the report useful not only as a project description but as a traceable record of the engineering work present in the codebase.
